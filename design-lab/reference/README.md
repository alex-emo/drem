# reference/ · 外部参考语料

这里存放**从外部整包取回、原样保存**的参考资料，和 `research/` 的手工摘录分开：

| 目录 | 内容 | 证据等级 |
|---|---|---|
| `research/` | 我们逐条抓取、逐字摘录、标注 URL 与日期的证据 | A（规范/官方文档）或 B（可靠二手） |
| `reference/` | 第三方打包的清单、速查表、风格指南原文 | 通常是 **C**：二次合成，不能当证据 |

判断规则：`research/` 里的条目可以支撑决策；`reference/` 只能**提出候选问题**，结论必须回到 A/B 级原文。

## 1. omd:feel（oh-my-design-cli）

- 来源包：`oh-my-design-cli@2.0.0`（npm）
- 抓取日期：2026-11-25
- 抓取方式：`https://unpkg.com/oh-my-design-cli@2.0.0/skills/omd-feel/<file>`，回执 HTTP 200
- 本地文件：

| 文件 | 字节 | 内容 |
|---|---|---|
| `omd-SKILL.md` | 12,385 | 审计流程、评分、严重度映射、输出格式 |
| `omd-reference.md` | 102,771 | 17 个维度、113 条规则（含 `🔍 machine_check`） |
| `omd-provenance.md` | 52,831 | 每条规则的来源分级与出处 |

- 规模：SPEC 61 / DS 24 / CONV 19 / OP 7 / FOLK 2（共 113）。SPEC 指 W3C/HIG/M3 等公开规范，DS 指已提交的设计系统 token，CONV 指 ≥2 个独立实践者，OP 是单人观点，FOLK 是无出处民俗。
- 它的严重度映射：SPEC/DS = BLOCK，CONV = WARN，OP/FOLK = FYI。**这套映射我们只借用它的分级语言，不照搬严重度**——因为它是面向 Web 的一次性审计，而 Dream 是 Flutter 移动端，有平台差异（44pt vs 48dp、CJK 行高、手势冲突）。
- 它的三条元规则我们直接接受，并且已经写进 `constraints.md` 的工作方式：
  1. 项目自己的 `DESIGN.md` / token 优先于清单；冲突时以项目为准，并记录理由。
  2. 不得把 folklore 当 spec；C 级规则只能触发提问。
  3. 不得发明数字；规则里没有具体值就不写具体值。

## 2. 使用方式

1. 用 `omd-reference.md` 当检查表扫一遍当前实现，把命中项写成「候选问题」，不是结论。
2. 每个候选问题回到 A/B 级原文找依据（W3C、HIG、M3、官方帮助中心）。
3. 找不到 A/B 依据的，要么降级成 FYI 记在审计文档里，要么放弃。
4. 审计结论与修复写进 `research/02-omd-feel-audit.md`；需要改代码的另开 decision。

## 3. 不做什么

- 不把 113 条规则逐条套到 Dream 上产出 113 条结论。清单是提问工具，不是验收标准。
- 不把它的评分当作设计质量分数；分数只用来排序候选问题。
- 不复制它的文案/风格到用户可见界面。
- 不因为它写了 50ms 网格就立刻改我们的动效 token——见审计文档里「暂缓」一节的理由。
